Lesson 0002 · 实测约 15 分钟讲解 + 13 分钟编译

本地 nativeCompile 与 nativeTest

本课的胜利条件：不用 Docker，直接生成、运行并测试一个 Spring Boot 4.1 原生可执行文件。

本课已在当前项目实测通过：应用原生编译耗时 6 分 49 秒，启动耗时 0.142 秒；原生测试构建耗时 5 分 58 秒，2/2 测试通过。

先分清两种 AOT

Spring Boot Native 里有两个层次的 Ahead-of-Time processing。它们名字相同，但解决的问题不同。

层次负责什么主要任务
Spring AOT 提前分析 Bean、自动配置、代理、反射和资源，把 Spring 的动态行为转换为生成代码与 hints。 processAot、aotClasses
GraalVM AOT 对字节码、Spring AOT 生成物和 reachability metadata 做静态分析，编译成目标平台机器码。 nativeCompile 
Java 源码
   ↓ javac
Java 字节码
   ↓
Spring AOT
   ├── Bean 注册代码
   ├── Proxy 信息或代码
   ├── Reflection hints
   └── Resource metadata
   ↓
GraalVM Native Image AOT
   ↓
Linux 原生可执行文件

应用 org.graalvm.buildtools.native 插件后，Spring Boot 会自动启用 Spring AOT。执行 nativeCompile 时不需要手工先跑 processAot。

检查题：谁负责提前处理 Spring Bean、自动配置和代理？

AOT 也能运行在 JVM 上

Spring AOT 并不只服务于 Native Image。下面的程序仍由 JRE 运行，但强制使用 AOT 生成的 Spring 初始化代码：

./gradlew bootJar
java -Dspring.aot.enabled=true \
  -jar build/libs/native-demo-0.0.1-SNAPSHOT.jar

它适合快速区分两类问题：

  • 如果 JVM + Spring AOT 已经失败，问题多半在 Bean 图、条件配置或 Spring AOT。
  • 如果 JVM + Spring AOT 正常，而 Native 失败，再检查 reflection、resources、JNI、动态代理或平台依赖。

第一步：建立 JVM 测试基线

./gradlew test

本课 JVM 基线为 BUILD SUCCESSFUL。这是必要的诊断边界：普通测试失败时，不要先怀疑 Native Image。

第二步：构建应用原生程序

./gradlew nativeCompile

当前项目的任务链：

processAot
compileAotJava
processAotResources
aotClasses
generateResourcesConfigFile
nativeCompile

本次构建环境：

JavaGraalVM CE 25.0.2
目标指令集x86-64-v3
C 编译器GCC 13.3.0
GCSerial GC
构建线程16
峰值 RSS5.15 GB

八个 Native Image 阶段

  1. Initializing
  2. Performing analysis
  3. Building universe
  4. Parsing methods
  5. Inlining methods
  6. Compiling methods
  7. Laying out methods
  8. Creating image

本次 closed-world analysis 找到 18,546 个可达类型、86,152 个可达方法，并为反射注册了 13,816 个方法。没有被证明可达、也没有 hints 的内容可能不会进入最终程序。

第三步：检查输出文件

ls -lh build/native/nativeCompile
file build/native/nativeCompile/native-demo
ldd build/native/nativeCompile/native-demo

主程序位于：

build/native/nativeCompile/native-demo

实测它是 stripped 的 Linux x86-64 PIE ELF，可执行文件约 84 MiB。直接动态依赖包括 libc、libz 和 ELF loader。

Native 不等于完全静态。Java 应用与必要运行时已经变成机器码，但程序仍可能依赖操作系统 ABI、动态库和特定 CPU 指令集。部署到另一台机器前要验证兼容性。

第四步：直接运行，不经过 Docker

./build/native/nativeCompile/native-demo \
  --server.port=8082

另开终端验证：

curl http://127.0.0.1:8082/hello

本课结果：

第五步：把测试也编译成原生程序

./gradlew nativeTest

nativeTest 会单独生成：

build/native/nativeTestCompile/native-demo-tests

它包含应用、测试代码、Spring Test、MockMvc 和 JUnit Platform Native 支持，所以不是简单地“拿现有应用二进制跑一次测试”。

检查题：nativeTest 是否只是运行 native-demo 应用程序？

应该记住的命令

./gradlew test快速 JVM 测试基线
./gradlew nativeCompile生成应用原生程序
./gradlew nativeRun构建并运行原生程序
./gradlew nativeTestCompile只生成原生测试程序
./gradlew nativeTest生成并运行原生测试
./gradlew bootBuildImage生成 Native OCI 镜像

推荐反馈顺序

./gradlew test
        ↓
JVM + spring.aot.enabled=true
        ↓
./gradlew nativeTest
        ↓
./gradlew nativeCompile
        ↓
./gradlew bootBuildImage
不要用 nativeTest 替代日常单元测试。JVM 测试适合频繁运行；关键边界、交付前检查和 reachability 修复才运行成本较高的原生测试。
