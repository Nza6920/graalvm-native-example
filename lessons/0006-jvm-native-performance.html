正确比较 JVM 与 Native

本课的胜利条件：不再用单次启动、单个文件大小或一句“Native 更快”下结论，而是按工作负载选择运行时。

本机结论：Native 冷启动约快 39 倍、就绪 RSS 低约 65%；但预热后的 JVM 吞吐量约高 38%。Native 优化的是启动和占用， 不承诺长期吞吐一定胜过 JVM。

先定义公平的实验

应用同一份 Spring Boot 4.1.0 代码
端点GET /hello，无数据库与外部网络
启动从创建进程到 HTTP 返回 2xx，交错执行 5 轮
吞吐先预热 5 秒，再用 wrk 测 3 × 10 秒
并发4 个压测线程，32 个连接
统计比较中位数，不挑选最好的一轮

客户端和服务端运行在同一台 WSL2 主机，因此这是当前项目的相对实验， 不是可移植到所有机器的产品性能数字。这里也没有清除操作系统页缓存， 所以准确名称是“新进程启动”，不是磁盘级绝对冷启动。

一条命令复现

cd native-demo
./gradlew bootJar nativeCompile
./benchmark/run-comparison.sh

脚本会生成 startup.tsv、throughput.tsv、 artifacts.tsv 和每轮原始 wrk 输出。完整参数说明见 benchmark/README.md。

结果一：启动与就绪内存

中位数JVMNative观察
启动到 HTTP 就绪5663.677 ms144.847 msNative 快 39.09×
就绪 RSS268588 KiB94624 KiBNative 低 64.8%

Native 在构建期完成了闭世界分析、AOT 处理和机器码编译，启动时不需要 启动 JVM、加载大量 class 并等待 JIT。因此它很适合按需扩容、CLI、短任务 和对容器内存密度敏感的服务。

结果二：预热吞吐与延迟

中位数JVMNative
吞吐量18597.64 req/s13427.63 req/s
p50 延迟1.476 ms2.070 ms
p95 延迟3.744 ms4.901 ms
压测期 RSS272976 KiB101424 KiB

本实验的 JVM 吞吐中位数比 Native 高 38.5%。HotSpot 会观察真实运行 路径，再由 JIT 编译和重新优化热点代码；长时间稳定运行时，这种自适应优化 可能超过构建期一次性完成的 AOT 编译。Native 仍保留明显的内存优势。

判断练习：根据本次结果，哪个结论最准确？

结果三：为什么 Native 单文件反而更大？

产物单文件大小运行依赖
Boot JAR19.13 MiB还需要匹配的 JRE 和系统环境
Native executable83.50 MiB不需要安装 JRE，仍依赖 OS/架构及少量动态库

Native 可执行文件包含应用、依赖中可达的机器码、镜像堆、资源和运行时 支撑代码，所以它比 JAR 大很正常。JAR 只是部署集合的一部分；公平的容器比较 应该比较完整 OCI 镜像、启动、RSS、安全更新流程和目标平台，而不是只比较 两个文件。

部署边界

问题JVMNative
跨平台JAR 可由目标平台的兼容 JRE 运行必须为目标 OS 与 CPU 架构构建
动态行为运行时更自由闭世界限制，动态特性需要 metadata
启动与密度通常启动更慢、RSS 更高通常启动更快、RSS 更低
长期热点JIT 可按真实负载持续优化没有 HotSpot JIT 的持续重编译
构建成本秒级到较短本次 Native Image 生成约 5 分钟

选择口诀

冷启动、弹性扩容、内存密度优先 → 先评估 Native
长期常驻、峰值吞吐、动态能力优先 → 先评估 JVM
最终决定                         → 用真实业务负载测量
