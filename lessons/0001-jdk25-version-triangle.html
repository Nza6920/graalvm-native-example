Lesson 0001 · 约 8 分钟

先锁定 JDK 25 版本三角

本课的胜利条件：你能在自己的服务目录中证明 Gradle、GraalVM 和 Native Image 任务分别由什么版本提供。

先讲结论：课程项目使用 Spring Boot 4.1.0、Gradle 9.5.1 和 GraalVM JDK 25.0.2。Gradle 从 9.1 起正式支持在 JDK 25 上运行；当前项目已经用这套版本完成 AOT 处理和 JVM 测试。

Native Image 到底做了什么？

普通 Spring Boot JAR 把大量决定留到运行时。Native Image 会在构建期从入口开始做静态可达性分析，只把需要的代码、运行时组件和资源编译进特定操作系统与架构的可执行文件。

这就是闭世界假设：运行时会用到的代码必须在构建期已知。反射、动态代理、JNI、序列化和按名称读取的资源之所以常出问题，是因为静态分析不一定能看见它们。Spring AOT 的工作，就是提前生成代码和提示，帮助 GraalVM 看见这些动态行为。

检索练习：Native Image 何时必须知道运行时可达的代码？

动手：四条命令建立事实

进入你的 Spring Boot 服务目录，执行：

java -version
./gradlew --version
native-image --version
./gradlew tasks --all

你要从输出中找到四件事：

  1. java 是否是 GraalVM JDK 25，而不只是任意 JDK 25。
  2. Gradle 版本是否至少为 9.1，以及 Gradle Daemon 实际使用哪个 JVM。
  3. native-image 是否存在且报告 JDK 25。
  4. 任务列表是否包含 nativeCompile；没有它通常意味着尚未应用 org.graalvm.buildtools.native 插件。
不要先改业务代码。如果前三条版本事实不清楚，后面的 AOT 或反射错误很容易被误诊。把四条命令的输出发给我，我会据此给你下一课的最小 build.gradle 修改。

原生构建流水线

Java 源码 → JVM 字节码 → Spring AOT 生成物 → GraalVM 可达性分析 → 本机原生可执行文件

注意最后一步是平台相关的：通常不能在 macOS 上直接构建 Linux 可执行文件。生产环境常在目标平台或匹配的容器构建环境中完成。
